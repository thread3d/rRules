### 1. Metrics Export Format

1. Text format only (standard Prometheus)

3. Both formats (accept-header driven) — **SELECTED**

**Notes:**

- JSON format supports dashboard API consumers
- Implementation complexity is acceptable for flexibility benefit

### 2. Dashboard Data Source

**Options presented:**
1. WebSocket streaming (real-time push)
2. HTTP polling (interval-based fetch)
3. Server-Sent Events (SSE)

**User selection:** WebSocket streaming — lowest latency for real-time dashboards

**Notes:**
- Existing frontend hook (`useEngineMetrics.ts`) already has WS + polling fallback
- Backend needs `/v1/metrics/ws` endpoint
- Consider load balancer compatibility in deployment docs

---

### 3. Dead Rule Detection Scope

**Options presented:**
1. All rules globally (no filtering)
2. By category filter
3. Configurable threshold with default 24h — **SELECTED**

**User selection:** Configurable threshold approach

**Notes:**
- Existing `SlidingWindowConfig` has 24h default via `DeadRuleConfig`
- Read threshold from config file or env variable (`DEAD_RULE_THRESHOLD_HOURS`)
- CLI flag `/api/v1/dead-rules?threshold_hours=XX` for one-off analysis

---

### 4. Coverage Reporting Depth

**Options presented:**
1. Rule-level firing only
2. Condition evaluation tracking
3. Full execution trace — **SELECTED**

**User selection:** Full execution trace (rule + conditions + working memory changes)

**Notes:**
- Maximum debugging capability
- Highest storage overhead, acceptable for production monitoring
- Existing `engine/src/monitoring/coverage.rs` has basic structure to extend

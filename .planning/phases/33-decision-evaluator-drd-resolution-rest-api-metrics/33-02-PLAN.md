<objective>
Implement multi-output evaluation and topological DRD resolution so that decisions referencing other decisions (via `required_decisions`) evaluate in correct dependency order, with cycle detection preventing infinite recursion. This delivers §10.4 compliance for the MVP scope lock: full decision-service support with multi-output, not single-decision-only.

Purpose: Without DRD resolution, a decision that depends on another decision's output can never receive that data — the multi-output evaluation surface (§10.4) would be non-functional for any real-world DMN model where decisions reference each other. Cycle detection prevents stack overflow on cyclic graphs (Pitfall 3).
Output: A working `DecisionEvaluator::evaluate()` that resolves DRD edges topologically, evaluates all referenced decisions first, merges their outputs into the scope, then evaluates the target decision and returns per-output values.
</objective>

  <name>Task 1: Implement topological DRD resolution with cycle detection</name>
  <files>engine/src/dmn/evaluator/mod.rs, engine/src/dmn/model.rs</files>
  <action>
    1. Add a private method `resolve_drd_order` to `DecisionEvaluator`:
       - Takes the model's definitions children and a target decision ID.
       - Builds an adjacency list: for each decision encountered, its `required_decisions` are outgoing edges.
       - Performs DFS topological sort (Kahn's algorithm or DFS with gray/black coloring).
       - Use gray/black coloring (Phase 31 boxed-context pattern) for cycle detection — if a gray node is revisited during DFS, the graph has a cycle.
       - Return `Result<Vec<String>, DecisionEvalError::DrdCycle>` where the Vec is in topological order (upstream first).

    2. Add a new variant to `DecisionEvalError`:
       ```rust
       #[error("DRD cycle detected involving decisions: {0:?}")]
       DrdCycle(Vec<String>),
       ```

    3. The topological sort must handle:
       - Decisions with no `required_decisions` (leaf nodes) — evaluate first.
       - Decisions that reference other decisions not in the current model (e.g., external system references) — skip with a warning log, do NOT error.
       - InputData nodes referenced via `required_inputs` — these are data sources, not evaluated; their values come from the request inputs or InformationItem defaults.

    4. Implementation pattern (follow Phase 31's boxed-context topological evaluation):
       ```rust
       fn resolve_drd_order(
           &self,
           target_id: &str,
       ) -> Result<Vec<String>, DecisionEvalError> {
           let guard = self.shared.read().map_err(...)?;
           // Build decision map: id -> &Decision for all decisions in model.
           let decision_map: HashMap<&str, &Decision> = extract_decisions(&guard.model)
               .into_iter()
               .map(|d| (d.id.as_str(), d))
               .collect();

           // DFS with gray/black coloring.
           enum Color { White, Gray, Black }
           let mut colors: HashMap<&str, Color> = decision_map.keys().copied().map(|k| (k, Color::White)).collect();
           let mut order = Vec::new();

           fn dfs(
               node: &str,
               decision_map: &HashMap<&str, &Decision>,
               colors: &mut HashMap<&str, Color>,
               order: &mut Vec<String>,
           ) -> Result<(), DecisionEvalError> {
               match colors.get(node).copied() {
                   Some(Color::Gray) => return Err(DecisionEvalError::DrdCycle(/* collect cycle */)),
                   Some(Color::Black) => return Ok(()),
                   _ => {}
               }
               colors.insert(node, Color::Gray);
               if let Some(decision) = decision_map.get(node) {
                   for dep_id in &decision.required_decisions {
                       // Only recurse into decisions that exist in the model.
                       if decision_map.contains_key(dep_id.as_str()) {
                           dfs(dep_id, decision_map, colors, order)?;
                       }
                   }
               }
               colors.insert(node, Color::Black);
               order.push(node.to_string());
               Ok(())
           }

           // Sort all decisions, but ensure target_id is last (it's the root).
           let mut all_ids: Vec<String> = decision_map.keys().map(|s| s.to_string()).collect();
           all_ids.sort();
           for id in &all_ids {
               dfs(id, &decision_map, &mut colors, &mut order)?;
           }

           // Filter to only decisions reachable from target_id.
           let mut result = Vec::new();
           fn collect_reachable(
               id: &str, decision_map: &HashMap<&str, &Decision>, reachable: &mut HashSet<String>
           ) {
               if reachable.contains(id) { return; }
               reachable.insert(id.to_string());
               if let Some(d) = decision_map.get(id) {
                   for dep in &d.required_decisions {
                       collect_reachable(dep, decision_map, reachable);
                   }
               }
           }
           let mut reachable = HashSet::new();
           collect_reachable(target_id, &decision_map, &mut reachable);

           // Return topological order filtered to reachable set.
           for id in order {
               if reachable.contains(&id) { result.push(id); }
           }
           Ok(result)
       }
       ```

    5. Add `use std::collections::HashSet;` at the top of the file.
  </action>
  <verify>
    Run `cargo test -p engine --lib dmn::evaluator -- --nocapture` after adding unit tests (see Plan 3 Wave 0). The topological sort must produce correct order for linear chains, diamond patterns, and detect cycles in A→B→A graphs.
  </verify>

<task type="auto">
  <name>Task 2: Enhance evaluate() for multi-output + DRD chaining</name>
  <files>engine/src/dmn/evaluator/mod.rs</files>
  <action>
    1. Modify `DecisionEvaluator::evaluate()` to use DRD resolution before table evaluation:
       - After finding the decision (step 2), call `resolve_drd_order(decision_id)` to get the topological order of all decisions that must be evaluated first.
       - For each upstream decision in order:
         a. Evaluate it by calling `self.evaluate(upstream_id, request_with_upstream_inputs)`.
         b. Merge its outputs into a shared "context" HashMap (keyed by the upstream decision's `variable.name` — this is how DRD edges propagate data per §10.4).
       - After all upstream decisions are resolved, evaluate the target decision with the merged context as additional scope bindings.

    2. BREAKING CHANGE — Replace the return type of `evaluate()`:
       - OLD signature (Phase 32): `fn evaluate(&self, ...) -> Result<Value, DecisionEvalError>` — returns a single aggregated Value for all outputs.
       - NEW signature: `fn evaluate(&self, ...)-> Result<HashMap<String, Value>, DecisionEvalError>` — returns per-output values keyed by output clause name (or decision name for DecisionService).
       - This is a breaking change that affects any caller. The Phase 32 tests that asserted single-Value semantics must be updated to assert on the HashMap keys.
       - Add a migration note in `engine/src/dmn/evaluator/mod.rs`:
         ```rust
         // BREAKING CHANGE (Phase 33): evaluate() now returns HashMap<String, Value>
         // instead of a single Value. Each key is an output clause name or decision name.
         // Callers that need the old behavior can use `result.into_values()` to flatten.
         ```

    3. Enhance the output mapping to produce per-output values:
       - For decisions with a `decision_table`: iterate `output_clauses`, and for each matched rule's output entries, evaluate the specific cell FEEL expression (not the aggregated result) to get that clause's individual Value.
       - This requires exposing the per-cell evaluation logic from `DecisionTableEvaluator`. Add a method like `evaluate_single_output(table, scope, cache, output_idx)` that returns just one output clause's value from the matched rule(s).
       - For decisions without a table (boxed expressions): evaluate the expression against the scope and return as a single-element map keyed by the decision's variable name.

    4. The merged context propagation: when an upstream decision `D1` with `variable.name = "credit_score"` is evaluated, its output value goes into the context under key `"credit_score"`. Downstream decisions that reference `${credit_score}` in their input clauses can then resolve it via FEEL's longest-match qualified name resolution (Phase 31).

    5. For DecisionService nodes (if the target is a `DecisionService` rather than a `Decision`):
       - Per §10.4, iterate `output_decisions`, evaluate each, and return all results as a map keyed by decision name.
       - This requires checking `DefinitionsChild::DecisionService` variants in the model's children list to find the service node.
       - The MVP scope (per SC-1) says "evaluate all outputs of one decision" — but the user locked decision says "FULL §10.4 decision-service support (multi-output)", so DecisionService evaluation IS in scope for this phase.

    6. Update `EvaluateResult` to include a `decision_name: Option<String>` field for DecisionService results that aggregate multiple decisions.
  </action>

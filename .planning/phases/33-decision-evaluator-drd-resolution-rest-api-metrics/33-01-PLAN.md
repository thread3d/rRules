  <files>engine/src/dmn/evaluator/mod.rs, api/src/v1/decisions.rs</files>
  <action>
    1. In `api/src/main.rs`, after creating the shared DMN model and DecisionEvaluator (from Task 1), create a reference to the dedicated DMN metrics registry:

       - No need to inject as web::Data — the LazyLock statics are process-global and safe to read from any handler.

    2. In `api/src/v1/decisions.rs`, modify `evaluate_decision` handler to instrument metrics:
       - BEFORE calling `evaluator.evaluate()`: increment `METRIC_EVALUATE_REQUESTS_TOTAL.with_label_values(&[&decision_id]).inc()`.
       - AFTER successful evaluate: record duration via `METRIC_EVALUATE_DURATION_SECONDS.with_label_values(&[&decision_id, &hit_policy_str]).observe(duration_secs)`, where `duration_secs = result.duration_ms / 1000.0` and `hit_policy_str` comes from the decision's table hit policy (or "None" if no table).
       - AFTER successful evaluate: increment `METRIC_RULES_FIRED_TOTAL.with_label_values(&[&decision_id, &hit_policy_str]).add(result.rules_fired as f64)`.
       - For error paths: still increment the request counter (it was already incremented before the call), but skip duration/rules counters.

    3. In `engine/src/dmn/evaluator/mod.rs`, enhance the `evaluate()` method to return per-output values instead of mapping all outputs to a single Value:
       - BREAKING CHANGE (see Plan 02 Task 2 for full contract): `evaluate()` return type changes from `Result<Value, DecisionEvalError>` to `Result<HashMap<String, Value>, DecisionEvalError>`. Each key is an output clause name or decision name; each value is the evaluated result.
       - The current code at lines 158-164 maps every output clause name to `result` (the same aggregated Value). This is wrong for multi-output decisions.
       - Replace with: iterate `table.output_clauses`, and for each, evaluate the table's matching rules but extract only that clause's output value from the matched rule(s) per the hit policy semantics.
       - For UNIQUE/ANY/FIRST/PRIORITY/RULE ORDER: find the single winning rule (per hit-policy dispatch), then extract `rule.output_entries[i]` and evaluate it as a FEEL expression against the scope to get that specific output's Value.
       - For OUTPUT ORDER/COLLECT: iterate all matched rules, collect per-output values across rules.
       - This requires exposing a new method on `DecisionTableEvaluator`: `evaluate_per_output(table, scope, cache) -> HashMap<String, Value>`. The old single-Value evaluation is no longer needed (the HashMap approach subsumes it).

    4. In the handler's error path, if the error is a `HitPolicyViolation`, return 400 with `DMN_HIT_POLICY_VIOLATION` error code (per ROADMAP key deliverable). Map it via:
       ```rust
       Err(engine::dmn::evaluator::DecisionEvalError::TableError(
           engine::dmn::decision_table::DecisionTableError::HitPolicyViolation { policy, message }
       )) => HttpResponse::BadRequest().json(serde_json::json!({
           "error_code": "DMN_HIT_POLICY_VIOLATION",
           "policy": policy,
           "message": message,
       }))
       ```

    CRITICAL: Never import or use `prometheus::default_registry()` — all metric operations must go through the named statics in `api::v1::dmn_metrics`. Pitfall 24-A: registering on default_registry panics with duplicate metric names.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API (untrusted) | All input to `POST /v1/decisions/{id}/evaluate` is untrusted — FEEL expressions in decision tables are validated by Phase 31 parser, but the request body's `inputs` HashMap values must be type-checked against the decision's expected variable types. |
| API→engine (trusted internal) | The evaluator reads from `SharedDmnModel` under a read lock; no untrusted code crosses this boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-33-01 | Tampering | evaluate handler input | medium | mitigate | Request body validated by `serde_json::Deserialize` + actix-web `web::Json`; FEEL expressions in decision tables pre-validated at load time (Phase 31). Input values typed against `InformationItem.type_ref` — reject mismatched types with 400. |
| T-33-02 | Information Exposure | /v1/metrics/dmn endpoint | low | accept | Metrics labels include only decision_id and hit_policy (no PII, no input values). Public endpoint matches existing `/metrics` design. |
| T-33-03 | Denial of Service | large DMN file reload | high | mitigate | File size limits in upload handler; `parse_dmn_with_cache` has DoS guards from Phase 29 (max_tokens, max_depth). Reload is synchronous — add a timeout guard (`tokio::time::timeout`) to prevent blocking the actix worker. |
| T-33-SC | Tampering | Prometheus metric names | high | mitigate | All metrics registered on dedicated `DMN_METRICS_REGISTRY` (not default_registry) — Pitfall 24-A avoidance. Verify at startup that no names collide with engine crate metrics. |
</threat_model>

<objective>
Refactor the frontend hit-policy data model from a flat list of 9 sibling policies to the DMN 1.5 canonical structure: 7 standard policies + COLLECT aggregators as sub-type parameters (per D-01 hybrid approach). This aligns the frontend vocabulary with `engine/src/dmn/model.rs` (the canonical IR) so that every downstream consumer — the serializer in Plan 02 and the evaluation wire-up in Plan 03 — works against one agreed shape.

Purpose: Eliminate the structural mismatch between frontend (`'sum'`, `'min'`, `'max'`, `'count'` as top-level siblings of `COLLECT`) and backend (7-variant HitPolicy enum + separate BuiltinAggregator). Use string enum validated against known set for API contract (per D-02), with aggregators integrated into COLLECT rather than separate policies (per D-03, D-04).

Output: Refactored types.ts, updated HitPolicySelector with COLLECT aggregator toggle, DecisionTable using the new model, unit tests covering DMN-30.
</objective>

    - The `interface HitPolicy { id, name, description, requiresAggregation? }` interface
    - The `HIT_POLICIES: HitPolicy[]` array (9 entries including sum/min/max/count as siblings)
    - The `HitPolicyId = (typeof HIT_POLICIES)[number]['id']` type alias

    **Add these exports in this exact order:**

    1. `export type HitPolicy = 'UNIQUE' | 'ANY' | 'PRIORITY' | 'FIRST' | 'RULE ORDER' | 'OUTPUT ORDER' | 'COLLECT'` — string union of exactly the 7 DMN spec values (uppercase, space in "RULE ORDER" and "OUTPUT ORDER")

    2. `export type Aggregator = 'SUM' | 'MIN' | 'MAX' | 'COUNT'` — string union for COLLECT aggregators

    3. `export const AGGREGATOR_POLICIES: HitPolicy[] = ['COLLECT']` — which hit policies support aggregation (only COLLECT per DMN spec)

    4. `export const DEFAULT_AGGREGATOR: Aggregator = 'SUM'` — default for new COLLECT tables

    5. `export const AGGREGATORS: { id: Aggregator; name: string }[]` with entries `{id:'SUM',name:'Sum'}`, `{id:'MIN',name:'Min'}`, `{id:'MAX',name:'Max'}`, `{id:'COUNT',name:'Count'}`

    6. `export interface HitPolicyMeta { id: HitPolicy; name: string; description: string; requiresAggregator: boolean }` — metadata shape

    7. `export const HIT_POLICY_META: Record<HitPolicy, HitPolicyMeta>` with spec-accurate descriptions (per DMN 1.5 Clause 8.2.12):
       - UNIQUE: "Only one rule can match. Multiple matches is a violation."
       - ANY: "Multiple rules can match; all must agree on outputs."
       - PRIORITY: "Select the matching rule whose output has highest allowedValues position."
       - FIRST: "First matching rule in document order wins. No conflict detection."
       - RULE ORDER: "All matching rules' outputs returned in document order."
       - OUTPUT ORDER: "All matching rules' outputs sorted by allowedValues enumeration."
       - COLLECT: "Collect all matching rule outputs; optionally aggregate (SUM/MIN/MAX/COUNT)."

    8. `export const HIT_POLICIES: HitPolicy[] = Object.keys(HIT_POLICY_META) as HitPolicy[]` — array form for dropdown rendering

    **Preserve unchanged:**
    - DecisionTableColumn interface (line 51-54) — keep as-is
    - DecisionTableRow interface (line 57-60) — keep as-is  
    - CellValidationState interface (lines 65-70) — keep as-is

    **CRITICAL:** Hit-policy values are EXACTLY the DMN spec strings (uppercase). The frontend must send these exact strings to the backend — never lowercase, never kebab-case. This aligns with `HitPolicy::as_str()` in model.rs which returns `"UNIQUE"`, `"ANY"`, etc.

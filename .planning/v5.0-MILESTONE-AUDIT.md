## Integration Findings (non-blocking WARNINGs)

### WARNING 1 — `rule_filter` is a dead input (FRONTEND-03)
- Frontend `TestRunner.tsx:130` sends `rule_filter: { name_pattern: ruleId }` on every Run (comment claims a "test this rule" UX).
- Backend `execute_single` (`api/src/v1/execution.rs:534-793`) **never reads** `req.rule_filter`; the engine loads ALL rules from the shared ruleset (`engine.load_ruleset(&guard.ruleset)`).
- Impact: with a multi-rule ruleset, the results panel shows aggregate `rules_fired`/`facts_after`, not scoped to the edited rule. Single-rule test fixtures + the human SC-1 click-through used single-rule setups, so this never surfaced.
- Also declared and unused at `api/src/models/execution.rs:19`.
- No REQ explicitly mandates `rule_filter` scoping → **non-blocking**, but the frontend's "test this rule" claim is silently unenforced. Worth a follow-up: either honor `rule_filter` server-side or stop sending it + fix the UX copy.

### WARNING 2 — `/metrics` HTML + JSON arms hardcode `active_sessions: 0` (MON-07)
- `api/src/metrics.rs:328` (HTML arm) and `:343` (JSON arm) hardcode `active_sessions: 0`.
- The Prometheus text arm (`:345-365`) gathers from `counters.registry` which includes the live `rrules_sessions_active` gauge (registered `main.rs:118-121`, set to `session_manager.len()` at `sessions.rs:248,296,307` and `execution.rs:891,956`).
- The WS broadcast (`execution.rs:710,961`) also populates `active_sessions: session_manager.len()`.
- Impact: a dashboard driven by `GET /metrics` with `Accept: text/html` or `application/json` shows 0 sessions; WS/Prometheus show the real count. Inconsistent surfaces for the same metric.
- Not in any SC (SC-1 = Prometheus text, SC-2 = WS, SC-3 = structural) → **non-blocking**. Worth a follow-up: have the HTML/JSON arms read the live gauge/count like the text arm.
